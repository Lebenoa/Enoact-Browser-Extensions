# Repository Guidelines

## Project Overview

Enoact browser extension (v2): a cross-browser (Chrome, Firefox, Edge) "presence" extension — shows what you're doing in your browser to others. It builds a Discord-Rich-Presence-style activity payload from the currently-watched YouTube / YouTube Music page or a live Twitch stream and pushes it over a local WebSocket to an Enoact Core server (`ws://127.0.0.1:5579/ws`).

Companion to the [Enoact Core](https://github.com/Lebenoa/Enoact) backend. Built with Extension.js v4 + Svelte 5 + UnoCSS.

## Architecture & Data Flow

Three runtime contexts, wired through the browser extension API:

```
background service worker (per-site settings, storage, injection)
   │  webNavigation.onCommitted → chrome.scripting.executeScript(site script)
   ▼
scripts/youtube.ts | scripts/youtube-music.ts | scripts/twitch.ts  (injected into matched pages)
   │  scrape DOM → JSON activity → diff-based SET/CLEAR
   ▼
per-tab WebSocket ws://127.0.0.1:5579/ws  →  Enoact Core server
```

Each tab owns its own WebSocket (one per site script), so Discord can display multiple activities with different `name`s simultaneously — e.g. a YouTube and a Twitch tab push two activities at once.

- **Settings flow**: Sidebar UI ↔ long-lived `chrome.runtime.connect({name:"sidebar"})` port ↔ background worker ↔ `chrome.storage.sync` under key `enoact_settings`. Settings are per-site `{ enabled, channel_info }` configs.
- **Sidebar** is the SPA that edits settings; **content scripts** only render the floating "Open sidebar" pill (Shadow DOM) and inject nothing scripted — injection is driven by the background worker, not the content script.
- All runtime messaging uses string-typed message envelopes (`{type, ...}`); the sidebar port defines its own protocol (see below).

### Message/port protocol (sidebar ↔ background)

Port name `"sidebar"`. Background→sidebar events: `SETTINGS_LIST` (items: `{name, enabled}[]`), `TOGGLE`, `GET_SETTINGS`, `SUCCESS`, `ERROR`. Sidebar→background: `TOGGLE {name}`, `GET_SETTINGS {site}`, `UPDATE_SETTINGS {name, settings}`.

Other message types: `CONFIG` (background→injected page script, `{type:"CONFIG", config}` — broadcast to all open tabs of a site whenever its settings change), `CONFIG_REQUEST` (injected script → background, answered with `CONFIG`), and `openSidebar` (ContentApp → `runtime.sendMessage`).

## Key Directories

- `src/` — extension source. `background.ts` (worker: settings, injection, config broadcast), `manifest.json`, `types.ts` (shared `Settings`/`Config` types), `sidebar/` (Svelte 5 settings SPA), `content/` (ContentApp pill + Shadow DOM bootstrap), `images/`, `public/` (assets + generated `uno.css`).
- `scripts/` — standalone injected per-site scrapers: `youtube.ts`, `youtube-music.ts`, `twitch.ts`. Compiled to `./scripts/<name>.js` referenced by `background.ts`.
- `dev-scripts/` — `dev.ts`, a custom runner that spawns `extension dev` + `unocss -w` concurrently with signal forwarding.
- `public/` — `uno.css` (generated by UnoCSS CLI; gitignored), icon assets.
- `dist/` — build artifacts (gitignored): per-browser dirs (`chrome/`, `firefox/`, `chromium/`, `extension-js/`) plus `extension-profile-*` browser profile dirs.

## Development Commands

Runtime is **Bun** (package manager and runner) — `bun.lock` committed.

```bash
bun install                          # deps
bun run dev                          # dev-scripts/dev.ts: `extension dev` + `unocss -w` together
extension start                      # build + launch in a managed browser
extension build                      # build for packaging (prod)
bun run build                        # same as above
bun run build:chrome|firefox|edge    # extension build --browser <b>
extension preview                    # run built extension without rebuilding
```

The `bun run build --browser chrome,firefox` form in README is stale — npm scripts call `extension build --browser <b>`; only the `extension` CLI takes `--browser`. Default `-b` target is `chromium`.

### Prod build & injected scripts

`scripts/` is auto-collected as an entrypoint **only in `extension dev`** (emits `scripts/<name>.js`). The **prod `extension build` bundles only manifest-referenced files**, so the injected scripts (`./scripts/youtube.js`, `youtube-music.js`, `twitch.js`) that the worker loads via `chrome.scripting.executeScript` would otherwise be omitted. They are declared as explicit rspack entries in `extension.config.js` under the `config` escape hatch (which Extension.js merges in both dev and prod):

```js
// extension.config.js
config: (cfg) => {
  cfg.entry = {
    ...(cfg.entry || {}),
    'scripts/youtube': './scripts/youtube.ts',
    'scripts/youtube-music': './scripts/youtube-music.ts',
    'scripts/twitch': './scripts/twitch.ts',
  }
  return cfg
}
```

Keep this list in sync with `defaultSettings` in `src/background.ts`: every site script and the emitted path (`scripts/<name>.js`) must match worker references.

Other `extension` subcommands available: `logs`, `reload`, `inspect`, `storage`, `open`, `publish`, `doctor`.

There is **no lint or test script**. Per-repo convention: verify by running the extension (`extension start` / `bun run dev`).

## Code Conventions & Common Patterns

- **Language**: TypeScript, `strict: true`, ESM (`"type":"module"`), `noEmit` (bundler emits), `extends @tsconfig/svelte`. Ambient types via `extension-env.d.ts` (`/// <reference types="extension/types" />` + browser polyfill).
- **Cross-browser branching**: `import.meta.env.EXTENSION_PUBLIC_BROWSER` drives `isFirefoxLike` detection; background.ts branches into `browser.*` for Firefox (MV2: `browserAction`/`sidebarAction`) vs `chrome.*` for Chromium (MV3: `action`/`sidePanel`). ContentApp sends `openSidebar` differently per browser. Keep this pattern for any new API call.
- **Manifest**: single `manifest.json` with per-browser keys prefixed `chromium:` / `firefox:` (Extension.js resolves them). MV3 on Chromium, MV2 on Firefox. Permissions: `sidePanel`, `scripting`, `storage`, `webNavigation` (+ Firefox host perms inline in permissions; Chromium in `host_permissions`).
- **Svelte 5 runes**: `$state(...)` for reactive state, `$props()` + `$bindable()` for component props (see `Checkbox.svelte`), `$derived`/`$effect` where applicable. `onx:` attribute style (`onclick`, `onsubmit`, `onchange`). Transitions via `svelte/transition` (`fade`) and `{#key}` blocks to re-run sections.
- **Styling** (two-track, keep both):
  - UnoCSS utilities inline in `.svelte` markup engines (e.g. `class="flex flex-col items-center"`, dark theme hand-rolled). Config `uno.config.ts` uses `presetWind4`, CLI scans `src/**/*`, outputs to `public/uno.css`.
  - Scoped plain CSS files per surface (`sidebar/styles.css`, `content/styles.css`) for components/dedicated styles (sidebar dark theme via CSS vars `--sidebar-*`; content pill). Content is isolated in a Shadow DOM to avoid leaking styles into the host page — keep fetching CSS as text and injecting into a `<style>` node.
- **Error handling**: try/catch around storage and messaging ops, `console.error` + safe default (e.g. `getSettings()` falls back to `defaultSettings`). No external logging.
- **State management**: no library — plain per-site config objects in `chrome.storage.sync`, deep-merged with `defaultSettings` (`mergeWithDefaults`). Defaults live in `background.ts` and are the single source of truth for what fields sites support.
- **Injected scripts**: `export default function initXxx()` (Extension.js content-script wrapper contract — worker calls it, no auto-run). Each site script delegates its config/boilerplate lifecycle (CONFIG_REQUEST, `CONFIG` listener, presence client) to `createSiteScript` in `scripts/site-script.ts` and only defines its activity getter plus SPA-navigation restarts. They are long-lived, interval-driven (3s `UPDATE_DELAY`) reporters that own a **per-tab WebSocket** to Core with exponential reconnect backoff (2s→30s) — one socket per tab, so Discord can display multiple activities with different `name`s simultaneously (e.g. YouTube + Twitch). They send `SET`/`CLEAR` only when the activity payload changes (JSON-diffed), re-sending the current payload after (re)connecting since the server may have lost state. Scraping prefers embedded page data over DOM selectors: `#movie_player.getPlayerResponse()` (falling back to the `ytInitialPlayerResponse` script tag) on YouTube/YouTube Music, `__INITIAL_STATE__.stream` on Twitch — with `data-a-target` DOM fallbacks on Twitch, since embedded JSON is initial-load only and goes stale on SPA navigation. Because site scripts run in the ISOLATED world, they cannot call page-JS APIs directly; the worker injects a MAIN-world shim (`playerResponseShim` in `background.ts`) that answers a DOM event by writing the live player response into a `data-enoact-player-response` attribute, which `scripts/player-response.ts` reads. SPA-navigation handling (`yt-navigate-finish` listener on YouTube/YouTube Music, pathname-polling interval on Twitch) restarts the client. Sent payload = Discord activity object (`{name, type, details, state, assets:{large_image,...}, timestamps:{start,end}}`; live Twitch stream omits `timestamps`). Scripts send a `null` activity when nothing is worth showing, converted to `CLEAR` on the wire. Pause policy is consistent across sites: while paused, scripts keep the activity but omit `timestamps` so the progress freezes instead of drifting (YouTube Music previously cleared on pause). Playback state (paused/currentTime) always reads the live `<video>` element — media-element properties stay current in hidden tabs while player-API getters go stale. Scripts report `null` while their site's `enabled` config is off; the worker broadcasts updated `CONFIG` to every open tab of a site (`broadcastConfig`) whenever its settings change, so toggles apply to already-open tabs immediately.
- **Commit style**: Conventional Commits — `feat:`, `fix:`, `Removed:`, `Update:` (e.g. `Feat: settings sidebar`, `Fixed: wrong license`).

## Important Files

- `src/manifest.json` — the single per-browser manifest definition.
- `src/background.ts` — worker: settings persistence (key `enoact_settings`), storage merge logic, webNavigation-driven script injection, sidebar port protocol, `CONFIG` dispatch after injection + `broadcastConfig` on settings changes.
- `src/types.ts` — exported shared shapes: `Config` / `Settings` / `SaveSettings` plus the full sidebar port protocol (`SidebarMessage` sidebar→background, `BackgroundMessage` background→sidebar). Note: `Settings[site]` = `{script, config}`, but persisted storage keeps only `config`.
- `src/sidebar/SidebarApp.svelte` — settings UI; `SETTINGS_INFO` map drives per-field rendering (rename/description/type/dependsOn). `Checkbox.svelte` — styled `$bindable` checkbox.
- `scripts/youtube.ts` / `scripts/youtube-music.ts` / `scripts/twitch.ts` — scrapers producing activity from embedded page JSON (`#movie_player` player response / `ytInitialPlayerResponse` on YouTube & YouTube Music, `__INITIAL_STATE__` on Twitch) with `data-a-target` DOM fallbacks where the JSON goes stale on SPA navigation; `player-response.ts` / `embedded-json.ts` hold the shared readers.
- `src/content/scripts.ts` — content-script bootstrap (Shadow DOM + CSS injection + `mount`).
- `dev-scripts/dev.ts` — dev orchestration.
- `extension.config.js` — per-browser profiles **and** the `config` escape hatch declaring the injected site scripts as prod-build entries (see Development Commands). `uno.config.ts`, `tsconfig.json`, `extension-env.d.ts`.

The old Extension.js template scaffolding (`template.spec.ts` / `template.meta.json`) has been removed; no test runner is configured — verify via `bunx tsc --noEmit`, `bunx svelte-check`, and running the extension.

## Runtime/Tooling Preferences

- **Bun** is the runtime + package manager (`bun install`, `bun run dev`); `bun.lock` committed, `package-lock.json` and `yarn.lock` gitignored.
- npm scripts run JS files directly (`dev-scripts/dev.ts` via `bun run`) and thin `extension` CLI wrappers.
- Node/Bun modules import from `node_modules` directly (bundle-time import.meta features like `import.meta.env.*` and `import.meta.url` are used — Extension.js handles bundling).
- No code formatter enforced; style follows existing files (4-space indent, single quotes in JS files, double quotes in Svelte/`json`).
- Generated files gitignored: `dist/`, `public/uno.css` (regenerate with `bun run dev` / `unocss -w`), `extension-env.d.ts`, `.extension-js/`, browser profiles.

## Testing & QA

- **No test framework or script is configured.** No vitest/jest/playwright deps.
- Verification is manual/runtime: `bun run dev` spawns both the extension dev server and the UnoCSS watcher, or `extension start` builds and launches a managed browser.
- Manual QA targets: YouTube watch page and music.youtube.com — enable the site, verify the "Open sidebar" pill renders, open the sidebar, toggle affected settings (`enabled`, `channel_info`), and confirm the injected script pushes a `SET`/`CLEAR` activity over `ws://127.0.0.1:5579/ws` (requires a running Enoact Core server).
- No coverage expectations defined.
